# P2-9 — Multi-language UI strings · Design

**Status:** Approved · **Date:** 2026-05-07 · **Ticket:** P2-9 (Phase 2, sized S, ~1 evening expandable to ~1.5 — full 3-locale ship)

The final ticket of Phase 2 (Polish & Release). Lays vue-i18n infrastructure across the SPA, extracts every hardcoded English string into a locale catalog, and ships working translations for English, Czech, and German. Czech and German are AI-drafted; Czech is reviewed by the operator (CS-fluent per `docs/BRAND.md` voice section); German ships alpha-quality with a CHANGELOG caveat.

The acceptance criteria from `docs/ROADMAP.md`:

> **AC:** UI language switches correctly; no hardcoded English strings remain in components.

This spec covers code, data, and translation workflow. The implementation plan derived from this spec lists 8 tasks; one of them (CS proofread) is a manual operator step.

## 1. Scope

### In scope

- Add `vue-i18n` v9 + `@intlify/unplugin-vue-i18n` Vite plugin to `packages/web/`. Composition-API mode (`legacy: false`).
- Create three flat JSON locale files at `packages/web/src/locales/{en,cs,de}.json`, eagerly bundled.
- Add `packages/web/src/i18n/index.ts` (vue-i18n instance + setup) and `packages/web/src/i18n/locale-detect.ts` (first-paint priority chain: localStorage cache > `navigator.language` prefix > fallback EN).
- Add `packages/web/src/stores/i18n.ts` Pinia store wrapping the active locale with reactive setter that mirrors writes to `localStorage`.
- Extract every hardcoded English string in `packages/web/src/**/*.vue` into `en.json`. Replace each occurrence with `t('namespace.key')` calls. Includes visible text plus accessibility attributes (`aria-label`, `placeholder`, `alt`, `title`).
- Generate AI-drafted `cs.json` and `de.json` from `en.json` using BRAND.md's voice section as a style guide.
- Operator (Adam) reviews `cs.json` and lands corrections in a follow-up commit before merging the PR.
- Extend the server's `Settings` payload with `uiLanguage: 'en' | 'cs' | 'de'`; mirror in `packages/web/src/api/types.ts`. Default to `'en'` when reading legacy rows that lack the field.
- Settings modal grows a "Display language" `<select>` above the existing "Detection language" picker. Saves through the existing dirty-state flush mechanism.
- Add `packages/web/src/__tests__/i18n/locale-completeness.test.ts` asserting every key in `en.json` exists in `cs.json` and `de.json`.
- Add `packages/web/src/__tests__/test-utils.ts` exposing a `createTestI18n()` helper. Update existing component-test mount calls to install the plugin alongside `createTestingPinia`.
- CHANGELOG entry under `apps/addon/CHANGELOG.md` for version `0.3.0` summarising the i18n addition. Bump `apps/addon/config.yaml` version `0.2.0` → `0.3.0`.
- Pre-merge grep verification: no human-readable text remains in components outside `t()` calls or `{{ t(...) }}` template expressions.

### Out of scope

- Translating `apps/addon/README.md` or any other markdown documentation. Add-on store listing renders English; a future P3 ticket can localise the listing if real users ask.
- Translating server logs, API error envelopes, or any backend-emitted strings. Server-emitted `error` codes (e.g., `'invite_required'`) stay machine-readable; components that display them map known codes to translated user-facing messages where rendered.
- Date/time/number formatting via `Intl.DateTimeFormat` / `Intl.NumberFormat`. The app shows entity counts as plain integers and confidence as percentages; locale-specific number separators don't matter for the alpha audience.
- ICU MessageFormat features beyond simple pluralization. Vue-i18n's pipe-separated plural form covers our 5-6 plural cases.
- Lazy-loading locale JSON. All three locales bundle eagerly (~6KB gzipped total) — switching is instant, no async-init dance.
- Translating the brand wordmark. `<h1 class="lovelacer-wordmark">lovelace<i>r</i></h1>` is brand-protected per `docs/BRAND.md` "the wordmark is the wordmark in any locale".
- Translating any text rendered inside the generated Lovelace dashboard. That's HA's domain — its own i18n system handles it.
- Removing or modifying the existing `Settings.language` field that controls room-detection. UI display language is a separate orthogonal axis.
- Submitting CS/DE translations to a translation-management platform (Crowdin, Lokalise, etc.). JSON files in git are sufficient for the alpha.

## 2. Tech stack

### vue-i18n v9 + @intlify/unplugin-vue-i18n

Industry-standard Vue i18n library. ~20KB gzipped. Composition-API integration via `useI18n()` composable. Vue DevTools shows current key + active locale in dev. Built-in plural rules for CS (3 forms: 1 / 2-4 / 5+) and DE (2 forms: 1 / other) — non-trivial to write correctly by hand, especially CS.

The unplugin handles JSON imports as message catalogs without runtime parsing overhead and enables the precompiled-message-format optimisation.

Bundle cost is acceptable for a launch-quality SPA. The CS plural-rules logic alone justifies the dependency.

## 4. First-paint locale detection

`packages/web/src/i18n/locale-detect.ts`:

```ts
import type { UiLocale } from './index.js'
const SUPPORTED: readonly UiLocale[] = ['en', 'cs', 'de']

function isSupported(value: unknown): value is UiLocale {
  return typeof value === 'string' && (SUPPORTED as readonly string[]).includes(value)
}

export function detectInitialLocale(): UiLocale {
  // 1. localStorage cache (instant first paint, no flash)
  const cached = localStorage.getItem('lovelacer.uiLocale')
  if (isSupported(cached)) return cached
  // 2. browser preference (e.g., 'cs-CZ' → 'cs', 'de-AT' → 'de')
  const prefix = navigator.language.split('-')[0]?.toLowerCase()
  if (isSupported(prefix)) return prefix
  // 3. fallback
  return 'en'
}
```

### Settings sync (after first paint)

When `useSettingsStore.loadFromServer()` resolves AND `Settings.uiLanguage` differs from the localStorage-cached value:

1. The settings store's loaded value wins (server is authoritative for cross-device sync).
2. Pinia watcher updates `useI18nStore.locale` to the server value.
3. The setter mirrors the change to localStorage so the next first-paint matches.

Race condition: if the user changes UI language before settings load completes, the user's choice is preserved (they explicitly acted; the not-yet-loaded server value is overwritten on save). Implementation detail: the watcher only fires on settings-store-load completion, not on local user actions.

## 5. Settings integration

### Server schema change

`packages/server/src/storage/settings-store.ts`:

```ts
export type UiLanguage = 'en' | 'cs' | 'de'

export interface Settings {
  language: SettingsLanguage // existing — room detection
  cardPack: SettingsCardPack
  sections: SettingsSections
  uiLanguage: UiLanguage // NEW
}
```

When loading a row that lacks the `uiLanguage` JSON field (legacy P2-6 rows), default to `'en'`. The store's load logic already uses `??` defaulting per-field; this change extends the same pattern.

`packages/web/src/api/types.ts` mirrors the server type. The `Settings` Pinia store's `effective` and `dirtyState` plumbing already covers any new field — adding `uiLanguage` requires only the type addition + a default value in the store's initial-state factory.

### Settings modal UX

Add a new `<select>` group at the top of the modal body, ABOVE the existing "Detection language" picker:

```vue
<label for="settings-ui-language" ...>{{ t('settings.uiLanguage.label') }}</label>
<select
  id="settings-ui-language"
  data-testid="settings-ui-language"
  :value="settings.effective.uiLanguage"
  @change="settings.setUiLanguage(($event.target as HTMLSelectElement).value as UiLanguage)"
>
  <option value="en">{{ t('settings.uiLanguage.option.en') }}</option>
  <option value="cs">{{ t('settings.uiLanguage.option.cs') }}</option>
  <option value="de">{{ t('settings.uiLanguage.option.de') }}</option>
</select>
```

`useSettingsStore.setUiLanguage(lang)` writes to `dirtyState`. On save, the field is flushed alongside `language`/`sections`/`cardPack`.

A second sync flow: when `dirtyState.uiLanguage` changes during editing, also update `useI18nStore.locale` immediately so the modal itself re-renders in the new language. Discarding unsaved changes reverts both.

## 6. Translation workflow

### Phase A — Infrastructure + EN extraction (Tasks 1-6 of the plan)

Implementer subagent extracts every English string into `en.json`, replaces each component-side occurrence with `t('key')`. After each component's sweep, the existing component test still passes because `createTestI18n()` installs the real EN locale, and the rendered text equals the asserted English.

### Phase B — AI-drafted CS+DE (Task 7)

Generate `cs.json` and `de.json` from `en.json`. The AI prompt embeds:

1. The full `en.json` source.
2. The Voice section of `docs/BRAND.md` (confident not loud; direct not chatty; warm not cute; Czech-friendly translations; avoid puns that don't survive translation).
3. Vue-i18n plural-form notes for CS (3 forms) and DE (2 forms).
4. The native-name convention (English / Čeština / Deutsch — language-self-named).

The output files commit as-is. Run the locale-completeness test to verify no missing keys.

### Phase C — CS proofread (operator step, before merge)

Adam (CS-fluent) reads `cs.json` end-to-end and lands corrections in a follow-up commit. Common patterns to watch for:

- Czech declension (e.g., "Continue" → "Pokračovat" not "Pokračování")
- Formality register (Lovelacer is direct/warm; tu/Vy choice — recommend tu-form for the HA-insider audience)
- Plural-form correctness (3-slot pipe form: `{count} entita | {count} entity | {count} entit`)
- Brand voice: keeping it confident but plain, no marketing fluff

DE ships AI-drafted with a CHANGELOG note inviting translation PRs. No mandatory operator review for DE before merge.

## 7. Tests

### Existing test churn

About 15-20 component test files use `mount(Component, { global: { plugins: [createTestingPinia(...)] } })`. Each file gets a single-line addition to install i18n:

```ts
import { createTestI18n } from '../test-utils.js'

mount(Component, {
  global: {
    plugins: [createTestingPinia({ ... }), createTestI18n()],
  },
})
```

Tests that assert visible text (e.g., `expect(wrapper.text()).toContain('Continue')`) keep passing because EN is what they assert. No content-string churn.

The only exception: tests asserting now-translated `data-testid` values won't change because `data-testid` is not translated. Tests asserting attribute strings via `.attributes('aria-label')` may need updating if they assert verbatim English; replace with `expect(...).toBeTruthy()` (presence only) or update to assert the EN literal value (current English).

## 10. Risks

1. **CS plural rules.** Vue-i18n's CS rules are correct out of the box (`@intlify/core-base` ships locale-rules.ts). Mitigation: explicit plural-rules smoke test in Task 2 catches any regression.

2. **`navigator.language` in tests.** `happy-dom` defaults to `'en-US'`, so detect tests must mock the property explicitly (`Object.defineProperty(navigator, 'language', ...)`). Standard pattern; no surprise.

3. **AI-drafted DE quality.** German grammar (gendered nouns, declension patterns) is more complex than EN/CS. Risk: a German-fluent user finds clunky phrasings. Mitigation:
   - CHANGELOG explicitly invites translation PRs.
   - `apps/addon/README.md` "Status" section mentions DE alpha-quality.
   - GitHub issue template (if any future) accepts translation issues.

4. **String inventory drift.** Components added during extraction sweeps might miss strings. Mitigation: the pre-merge grep is documented as a verification step. If a string slips, the cs/de locales fall back to en (vue-i18n's `fallbackLocale` setting), preventing visual breakage — only an English peek-through.

5. **Test snapshot churn.** No tests use snapshot assertions today (`expect(wrapper.html()).toMatchSnapshot()` doesn't appear in the codebase), so the i18n swap doesn't cascade into snapshot updates. Confirmed via `grep -r "toMatchSnapshot" packages/web/src/__tests__`.

6. **Settings modal flicker on locale change.** Switching locale while modal is open causes immediate re-render with new strings. Acceptable UX — visible change confirms the choice took effect.

7. **localStorage unavailable (e.g., private browsing in some configs).** `detectInitialLocale()` falls through to `navigator.language` → `'en'`. The setter writes to localStorage but wraps in try/catch defensively (no test for this; common-sense robustness).

8. **`Settings.uiLanguage` field naming collision.** Existing `Settings.language` controls room detection. Documenting the orthogonality in `Settings` interface JSDoc + naming the new field `uiLanguage` (not `displayLanguage` or `interfaceLanguage`) keeps things searchable.
