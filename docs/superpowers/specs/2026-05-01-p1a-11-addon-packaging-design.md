# P1a-11 Add-on Packaging — Design

**Status:** Draft v1 · **Date:** 2026-05-01 · **Ticket:** [P1a-11 in `docs/ROADMAP.md`](../../ROADMAP.md)

## Goal

Ship a Home Assistant Add-on built from `@lovelacer/server` (Fastify) + `@lovelacer/web` (Vue SPA) so users can install Lovelacer through the HA Add-on Store via a custom repository URL. Target the Phase 1a alpha demo: install → click Analyze → click Apply → dashboard appears in HA, end-to-end in under 5 minutes.

## Non-goals

- Public HA Add-on Store listing. Custom-repo-only for the alpha — `https://github.com/Studio81Labs/lovelacer`.
- Polished branding. Placeholder PNGs generated by a script; real logo lands when there is one.
- ARM v6 / armhf / i386 support. Three arches (aarch64, amd64, armv7) cover ~99% of HA OS installs.
- s6-overlay / bashio. `init: false` and a plain shell entrypoint — fewer moving pieces.
- HA Supervisor API access. The backend talks to HA Core via the standard `homeassistant:8123` WebSocket using `SUPERVISOR_TOKEN`. No `hassio_api`, no `homeassistant_api`, no `host_network`.
- Drag-and-drop / per-entity overrides UI exposed through add-on options. Surface stays minimal: `log_level` + `dashboard_url_path`.
- Automated end-to-end tests against a real HA Supervisor. The dev HA container is HA Core, not Supervisor — manual smoke owns this gate.

## Approach summary

A single `apps/addon/` directory in this repo holds the add-on definition: `Dockerfile`, `build.yaml`, `config.yaml`, `run.sh`, `apparmor.txt`, `icon.png`, `logo.png`, `README.md`, `CHANGELOG.md`. Users add the repo URL as a custom add-on repository and HA Supervisor finds Lovelacer automatically.

Multi-arch builds use the official `home-assistant/builder` GitHub Action driven by two workflows: `build-addon.yml` (matrix over the three arches, runs on every PR + main push) and `release.yml` (orchestrator on tag pushes, calls `build-addon.yml` and creates the GitHub Release). Two image channels: `main` / `sha-<short>` for our dogfood loop and `latest` / `vX.Y.Z` for tagged alpha releases.

The backend gains one new env var: `DASHBOARD_URL_PATH` (default `lovelacer-home`), threaded through `runApply` so the add-on's `dashboard_url_path` option overrides `applyDashboard`'s default. The user's request body still wins per the existing hybrid-mode pattern.

Branding assets are reproducibly generated by a `dev/scripts/generate-addon-assets.ts` script and committed (HA needs them at install time) so a future logo change is a one-script run.

## Components

### 1. `apps/addon/config.yaml` — add-on metadata

```yaml
name: Lovelacer
version: '0.0.1'
slug: lovelacer
description: Generate a Lovelace dashboard from your Home Assistant entities
url: https://github.com/Studio81Labs/lovelacer
arch:
  - aarch64
  - amd64
  - armv7
init: false
ingress: true
ingress_port: 3000
panel_icon: mdi:home-variant
panel_title: Lovelacer
homeassistant_api: false
hassio_api: false
host_network: false
apparmor: true
options:
  log_level: info
  dashboard_url_path: lovelacer-home
schema:
  log_level: list(trace|debug|info|warn|error|fatal)
  dashboard_url_path: match(^[a-z0-9][a-z0-9-]*$)
image: ghcr.io/studio81labs/lovelacer-{arch}
```

Notable choices:

- **`init: false`** — no s6-overlay; `run.sh` is plain bash that `exec`s the Node server. Smaller image, simpler entrypoint.
- **`ingress: true` + `ingress_port: 3000`** — Supervisor proxies `/api/hassio_ingress/<token>/...` → `http://addon:3000/...`. The SPA's document-relative URLs (e.g., `api/preview`) resolve correctly inside the ingress prefix.
- **`panel_icon` + `panel_title`** — adds a "Lovelacer" entry in HA's sidebar that opens the SPA via ingress (one-click access).
- **No `homeassistant_api` / `hassio_api` / `host_network`** — minimal blast radius. The backend talks to HA Core via the standard WS endpoint inside the add-on network using `SUPERVISOR_TOKEN`, which Supervisor injects regardless of these flags.
- **`apparmor: true`** — strict profile, allowed syscalls listed in `apparmor.txt`.
- **`image:`** — Supervisor replaces `{arch}` based on the host arch when pulling.
- **`schema`** validates user input. `log_level` is a closed enum; `dashboard_url_path` is a HA-style URL slug regex.
- **`version: '0.0.1'`** — the version label on the published image. Bumped atomically with each tagged release.

### 2. `apps/addon/build.yaml`

```yaml
build_from:
  aarch64: ghcr.io/home-assistant/aarch64-base:3.21
  amd64: ghcr.io/home-assistant/amd64-base:3.21
  armv7: ghcr.io/home-assistant/armv7-base:3.21
labels:
  org.opencontainers.image.source: https://github.com/Studio81Labs/lovelacer
  org.opencontainers.image.licenses: MIT
```

Alpine 3.21 base. The HA builder reads this when invoked via the `home-assistant/builder` action.

### 3. `apps/addon/Dockerfile` — single-stage multi-arch build

```dockerfile
ARG BUILD_FROM
FROM ${BUILD_FROM}

# Alpine 3.21 ships Node 22 LTS in the main repo.
RUN apk add --no-cache nodejs npm jq

# Enable corepack so the project's pinned pnpm version (from
# package.json's `packageManager` field) is used at build time.
RUN corepack enable

WORKDIR /app

# Copy lockfile + workspace manifests first for cache-friendly install.
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json tsconfig.base.json ./
COPY packages/shared/package.json packages/shared/
COPY packages/analyzer/package.json packages/analyzer/
COPY packages/generator/package.json packages/generator/
COPY packages/ha-client/package.json packages/ha-client/
COPY packages/server/package.json packages/server/
COPY packages/web/package.json packages/web/

RUN pnpm install --frozen-lockfile

# Now copy the source.
COPY packages packages

# Build server (TS → dist/) and web (Vite → dist/).
RUN pnpm --filter @lovelacer/server build \
 && pnpm --filter @lovelacer/web build

# Drop devDependencies AFTER build to shrink the runtime image.
# Workspace symlinks remain intact so packages/server can resolve
# its workspace dependencies.
RUN pnpm install --frozen-lockfile --prod --ignore-scripts

# Entrypoint
COPY apps/addon/run.sh /run.sh
RUN chmod +x /run.sh

EXPOSE 3000

CMD ["/run.sh"]
```

**Single-stage rationale:** `home-assistant/builder` invokes `docker build` per arch with QEMU emulation. Multi-stage builds compound the emulation cost and break some of the action's caching expectations. Single stage with a final `pnpm install --prod` prune is the convention in HA add-ons.

**`.dockerignore`** at repo root excludes `node_modules`, `dist`, `.worktrees`, `tests`, `dev`, `docs`, `.git`, `.github`, etc. — only the paths the Dockerfile actually `COPY`s ship in the build context.

### 4. `apps/addon/run.sh`

```bash
#!/usr/bin/env bash
set -e

# Read add-on options. Without bashio (init: false), parse JSON directly.
OPTIONS_FILE="/data/options.json"
if [[ -f "$OPTIONS_FILE" ]]; then
  export LOG_LEVEL="$(jq -r '.log_level // "info"' "$OPTIONS_FILE")"
  export DASHBOARD_URL_PATH="$(jq -r '.dashboard_url_path // "lovelacer-home"' "$OPTIONS_FILE")"
fi

# Supervisor injects SUPERVISOR_TOKEN automatically.
export HA_URL="http://homeassistant:8123"
export DATA_DIR="/data"

cd /app
exec node packages/server/dist/main.js
```

`exec` replaces the shell so signals (SIGTERM from Supervisor on stop) reach Node directly.

### 5. `apps/addon/apparmor.txt` — strict + Node syscalls

```
#include <tunables/global>

profile lovelacer flags=(attach_disconnected,mediate_deleted) {
  #include <abstractions/base>
  #include <abstractions/nameservice>
  #include <abstractions/openssl>
  #include <abstractions/python>

  capability net_bind_service,
  capability dac_override,

  network inet stream,
  network inet6 stream,
  network unix stream,

  /usr/bin/node ix,
  /usr/bin/jq ix,
  /usr/bin/bash ix,

  /run.sh r,
  /app/** r,
  /data/** rw,
  /tmp/** rwk,
  /proc/sys/kernel/random/uuid r,
}
```

Allows: TCP listen on :3000, DNS lookup of `homeassistant`, file reads under `/app`, read/write under `/data` and `/tmp`. Denies: everything else by default.

### 6. Backend changes — `DASHBOARD_URL_PATH` plumbing

**`packages/server/src/config.ts`:**

```ts
const ConfigSchema = z.object({
  // ... existing fields ...
  DASHBOARD_URL_PATH: z
    .string()
    .regex(/^[a-z0-9][a-z0-9-]*$/)
    .default('lovelacer-home'),
})

export const config = {
  // ... existing fields ...
  dashboardUrlPath: parsed.DASHBOARD_URL_PATH,
} as const
```

**`packages/server/src/pipeline.ts`** — `runApply` accepts a default options object:

```ts
export async function runApply(
  ha: HaClient,
  body: ApplyInput,
  defaultOptions: ApplyDashboardOptions = {},
): Promise<ApplyDashboardResult> {
  const options = { ...defaultOptions, ...body.options } // body wins
  if (body.config !== undefined) {
    if (typeof body.config.title !== 'string' || !Array.isArray(body.config.views)) {
      throw new InvalidConfigError('invalid_config: title must be string and views must be array')
    }
    return ha.applyDashboard(body.config, options)
  }
  const preview = await runPreview(ha)
  return ha.applyDashboard(preview.config, options)
}
```

**`packages/server/src/routes/apply.ts`:**

```ts
export interface ApplyRouteOptions {
  ha: HaClient
  dashboardUrlPath: string
}

// inside the handler:
const result = await runApply(opts.ha, body, { urlPath: opts.dashboardUrlPath })
```

**`packages/server/src/app.ts`** — `CreateAppOptions.dashboardUrlPath: string`. `createApp` passes it through to `applyRoute`.

**`packages/server/src/main.ts`** — `await createApp({ ha, isDev, logLevel: config.logLevel, logger, dashboardUrlPath: config.dashboardUrlPath })`.

The existing hybrid mode is preserved: a request with `body.options.urlPath` still wins over the server config. This means custom-frontend consumers (P1b drag-and-drop UI) can still target a different URL path without restarting the add-on.

### 7. CI workflows

**`.github/workflows/build-addon.yml`:**

```yaml
name: Build add-on

on:
  push:
    branches: [main]
    paths:
      - 'apps/addon/**'
      - 'packages/**'
      - 'pnpm-lock.yaml'
      - 'package.json'
      - 'pnpm-workspace.yaml'
      - 'tsconfig.base.json'
      - '.github/workflows/build-addon.yml'
  pull_request:
    paths:
      - 'apps/addon/**'
      - 'packages/**'
      - 'pnpm-lock.yaml'
      - 'package.json'
      - 'pnpm-workspace.yaml'
      - 'tsconfig.base.json'
      - '.github/workflows/build-addon.yml'
  workflow_call:
    inputs:
      version:
        type: string
        required: true
      tags:
        type: string
        required: true
        description: 'Comma-separated additional image tags'

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        arch: [aarch64, amd64, armv7]
    steps:
      - uses: actions/checkout@v4

      - name: Login to GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Resolve build metadata
        id: meta
        run: |
          if [[ "${{ github.event_name }}" == "workflow_call" ]]; then
            echo "version=${{ inputs.version }}" >> "$GITHUB_OUTPUT"
            echo "tags=${{ inputs.tags }}" >> "$GITHUB_OUTPUT"
          elif [[ "${{ github.event_name }}" == "pull_request" ]]; then
            SHA="${GITHUB_SHA::7}"
            echo "version=0.0.0-pr.${{ github.event.number }}.${SHA}" >> "$GITHUB_OUTPUT"
            echo "tags=" >> "$GITHUB_OUTPUT"
          else
            SHA="${GITHUB_SHA::7}"
            echo "version=0.0.0-main.${SHA}" >> "$GITHUB_OUTPUT"
            echo "tags=main,sha-${SHA}" >> "$GITHUB_OUTPUT"
          fi

      - name: Build add-on (${{ matrix.arch }})
        uses: home-assistant/builder@2024.08.2
        with:
          args: |
            --${{ matrix.arch }}
            --target apps/addon
            --image ghcr.io/studio81labs/lovelacer-{arch}
            --version ${{ steps.meta.outputs.version }}
            ${{ steps.meta.outputs.tags != '' && format('--addtional-tag {0}', steps.meta.outputs.tags) || '' }}
            ${{ github.event_name == 'pull_request' && '--no-cache' || '' }}
```

PR builds skip GHCR login and don't push images — they exist purely to verify the Dockerfile compiles for all three arches before merge. Push-to-`main` builds publish under the `main` channel; tag releases publish under `latest` + `vX.Y.Z`.

**`.github/workflows/release.yml`:**

```yaml
name: Release

on:
  push:
    tags: ['v*']

permissions:
  contents: write
  packages: write

jobs:
  build:
    uses: ./.github/workflows/build-addon.yml
    with:
      version: ${{ github.ref_name }}
      tags: ${{ format('latest,{0}', github.ref_name) }}

  release:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
          tag_name: ${{ github.ref_name }}
```

### 8. Branding assets

**`dev/scripts/generate-addon-assets.ts`** uses Node's built-in `node:zlib` + a tiny PNG encoder (or, more pragmatically, the `pngjs` dev dep) to generate two PNGs from a hardcoded config:

- **`icon.png`** — 128×128, brand-orange (`oklch(0.62 0.19 35)` from the existing CSS theme) background, white "L" centered.
- **`logo.png`** — 250×100, brand-orange background, white "Lovelacer" text in Inter or system sans-serif.

The script is a regenerable artifact. Running it commits the PNGs deterministically. P1b/P2 can replace them with real designed assets.

To avoid pulling a heavy image lib, the script uses a minimal canvas approach: `sharp` is widely available and fast (~3 MB dep, dev-only). Falling back: if `sharp` is too heavy, hand-encode PNGs with raw RGBA buffers + `node:zlib` deflate (about 50 LOC). Decided in implementation.

## Data flow (runtime)

```
HA Supervisor
  │ pull ghcr.io/studio81labs/lovelacer-<host_arch>:<version>
  │ mount /data (persistent volume)
  │ write /data/options.json (user options)
  │ inject SUPERVISOR_TOKEN env var
  │ launch container: /run.sh
  ▼
/run.sh
  │ jq /data/options.json → LOG_LEVEL + DASHBOARD_URL_PATH
  │ HA_URL=http://homeassistant:8123
  │ DATA_DIR=/data
  │ exec node packages/server/dist/main.js
  ▼
Fastify on :3000
  │ HaClient → ws://homeassistant:8123/api/websocket (SUPERVISOR_TOKEN)
  │ Serves SPA from packages/web/dist
  │ /api/health, /api/analyze, /api/preview, /api/apply
  ▼
HA Supervisor ingress
  │ User opens "Lovelacer" from sidebar
  │ Supervisor: /api/hassio_ingress/<token>/ → http://addon:3000/
  │ SPA loads under that prefix; document-relative URLs resolve
```

## Error handling

| Layer           | Failure                                               | Behavior                                                                                                                              |
| --------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Container start | Missing `nodejs`/`jq`                                 | apk install fails at build time — caught in CI                                                                                        |
| `run.sh`        | `/data/options.json` missing                          | Falls back to env-var defaults via `jq -r '… // "default"'`                                                                           |
| `run.sh`        | `jq` parse error                                      | Default values still applied; LOG_LEVEL=info, DASHBOARD_URL_PATH=lovelacer-home                                                       |
| Server start    | `SUPERVISOR_TOKEN` and `HA_TOKEN` both absent         | Existing `config.ts` throws "No HA token configured" — Supervisor sees crash, restarts add-on                                         |
| Server start    | HA WS unreachable (Supervisor still bringing up Core) | Existing `setupRetry: -1` retries forever with backoff                                                                                |
| Apparmor denial | Unexpected syscall                                    | Container can't `exec` whatever it tried; logs surface in HA's add-on log viewer; we add the syscall to `apparmor.txt` and re-release |
| Image pull      | Manifest missing for host arch                        | Supervisor errors before starting; user sees "no compatible architecture" — solved by ensuring all 3 arches publish                   |

The existing `/api/health` endpoint stays the canary Supervisor uses for the add-on's health gauge.

## Testing

**Automated (CI on every PR):**

- `pnpm typecheck` clean across all 6 packages.
- `pnpm -r test` clean — including 2 new pipeline tests for `runApply` defaults.
- `pnpm format:check` and `pnpm lint` clean.
- `build-addon.yml` builds all 3 arches (aarch64, amd64, armv7). PR builds don't publish; just verify the Dockerfile compiles.

**New unit tests (`packages/server/src/__tests__/pipeline.test.ts`):**

- `runApply(ha, body, { urlPath: 'foo' })` with no `body.options` → `applyDashboard` called with `{ urlPath: 'foo' }`.
- `runApply(ha, { options: { urlPath: 'bar' } }, { urlPath: 'foo' })` → body wins, `applyDashboard` called with `{ urlPath: 'bar' }`.

**Manual smoke (the implementer, before PR merge):**

1. Build amd64 image locally:

   ```bash
   docker build -f apps/addon/Dockerfile \
     --build-arg BUILD_FROM=ghcr.io/home-assistant/amd64-base:3.21 \
     -t lovelacer-addon-local .
   ```

2. Run standalone against dev HA:

   ```bash
   docker run --rm -p 3000:3000 \
     -e HA_URL=http://host.docker.internal:8123 \
     -e HA_TOKEN=<dev-token-from-.env> \
     -e LOG_LEVEL=debug \
     -v /tmp/lovelacer-data:/data \
     lovelacer-addon-local
   ```

3. Open `http://localhost:3000` → Analyze → Apply → confirm `lovelacer-home` dashboard exists in dev HA.

**Manual smoke on real HA (after PR merge, before tagging v0.0.1):**

1. Push to `main` → CI publishes `main`-channel image automatically.
2. On a real HA install: Settings → Add-ons → Add-on Store → ⋮ → Repositories → add `https://github.com/Studio81Labs/lovelacer`.
3. Install Lovelacer from the resulting repo entry.
4. Configure (defaults are fine), start.
5. Click "Open web UI" or the sidebar entry.
6. Run Analyze → Apply.
7. Verify the new dashboard appears in HA and renders.
8. Time the flow — target < 5 minutes per the roadmap's Phase 1a demo.

## Dependencies

- New devDep: `sharp` for the PNG generation script (or hand-rolled PNG via `node:zlib` if size matters; decided in implementation).
- No new runtime deps. The Dockerfile installs `nodejs`, `npm`, `jq` from Alpine packages at build time.
- New CI deps (GitHub Actions): `home-assistant/builder@2024.08.2`, `docker/login-action@v3`, `softprops/action-gh-release@v2`. Pinned versions; renovate / dependabot can bump them later.

## Open questions resolved during brainstorming

- **Add-on location (Q1):** In-repo at `apps/addon/`. P2 may move to a separate `lovelacer-addon` repo for the public listing.
- **Multi-arch builder (Q2):** `home-assistant/builder` GitHub Action. Three arches: aarch64, amd64, armv7.
- **Add-on options (Q3):** `log_level` + `dashboard_url_path`. The latter brings a small backend plumbing change.
- **Security profile (Q4):** Minimal — `init: false`, `ingress: true`, no `homeassistant_api`/`hassio_api`/`host_network`, strict apparmor.
- **CI triggers (Q5):** Both — push to `main` publishes `main`-channel images, tag pushes publish `latest` + `vX.Y.Z`.
- **Branding (Q6):** Generated placeholder PNGs via `dev/scripts/generate-addon-assets.ts`, committed to the repo.

## Risks

- **HA Supervisor schema changes.** The `config.yaml` schema is stable but evolves. Mitigation: pin `home-assistant/builder` to a known-good version; bump deliberately when HA releases new features we want.
- **Multi-arch QEMU performance.** Cross-compilation in CI is slow (~5–10 min per arch). Acceptable for an alpha; P2 can move to native runners if we hit GitHub Actions quotas.
- **Apparmor denials in production.** We can't reproduce every Node syscall path locally; an unexpected denial in some user's environment will require a fast follow-up release. Mitigation: keep the apparmor profile permissive enough for Node + jq; treat denials as bugs and patch quickly.
- **Add-on options bypassed by frontend body.** The hybrid `runApply` lets a request body override server defaults. This is intentional (P1b drag-and-drop UI needs it) but means `dashboard_url_path` set in HA add-on options can be ignored if a frontend explicitly sends `body.options.urlPath`. Documented in the user-facing README.
- **GHCR rate limits or auth changes.** Anonymous pulls are rate-limited; logged-in pulls aren't. HA Supervisor pulls anonymously by default; if we hit rate limits during the alpha rollout, we publish a `docker-mirror` workflow to mirror to a CDN. Out of scope for P1a.
