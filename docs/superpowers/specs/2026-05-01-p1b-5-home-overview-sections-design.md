# P1b-5 — Home overview: full sections

**Status:** Design approved 2026-05-01

**Goal:** Fill out the dashboard's first view with the four homepage sections promised by `DASHBOARD_GENERATION.md`. Currently the Home view ships only Welcome + Quick stats (P1a-7). This ticket adds People, Active Rooms (live-state filtered via HA conditional cards), Scenes, and Cameras — all generated by the pure-function builder in `packages/generator/src/home-view.ts`.

**Out of scope:**
- Bulk/configurable section enabling/disabling (Add-on options) — that's a future ticket; for P1b-5 sections appear when their data exists.
- Mushroom card pack integration — Core cards only.
- Cross-language scene-name filtering (German/Czech). The "test"/"setup" keyword filter is English-only at MVP.
- HA template logic beyond `state` and composite `or` conditions (no `numeric_state`, `screen`, etc.).
- New entity-domain routing in the analyzer (`person`, `scene`, `camera` already flow through; no `domainGroup()` changes).

---

## Architecture

`buildHomeView()` grows from 2 sections to up to 6:

```
HA registries → normalize → detect → applyOverrides → groupByDomain
                                                          │
                                                          ▼
                       buildHomeView({ entities, groupings })
                       ├─ Welcome (existing)
                       ├─ Quick stats (existing)
                       ├─ People (new)
                       ├─ Active Rooms (new — uses groupings)
                       ├─ Scenes (new)
                       └─ Cameras (new)
```

Existing `buildWelcomeSection()` and `buildQuickStatsSection()` are untouched. Four new builders are added, each returning `GridSection | null`. `null` means "skip — no qualifying data".

**Module location:** `packages/generator/src/home-view.ts` (existing file). All four new builders live in the same file — they share the same domain logic (filter `entities` by domain, build cards, return a `GridSection`) and follow the existing `buildQuickStatsSection` pattern.

**Pipeline integration:** `runPreview` in `packages/server/src/pipeline.ts` passes `state.groupings` to `buildHomeView`. The single-line change at the call site:

```ts
const home = buildHomeView({ entities: state.entities, groupings: state.groupings })
```

**Pipeline state already has `groupings`:** the existing `PipelineState` interface in `pipeline.ts` already exposes `groupings: RoomGrouping[]`. No new pipeline state field needed.

**Type surface additions** in `packages/generator/src/lovelace-types.ts` are bounded:
- `ConditionalCard` interface
- `StateCondition`, `OrCondition`, `ConditionEntry` types
- `NavigateAction` interface
- `TileCard` gains optional `name?` and `tap_action?: NavigateAction` fields
- `LovelaceCard` discriminated union grows by `ConditionalCard`

These are additive — existing tile/heading/etc. consumers keep working. The one consumer that switches on `card.type` is the `entityIdsInCard()` helper in `room-view.fixtures.test.ts`; it gains a `'conditional'` arm that recurses into `card.card`.

## New card type additions

In `packages/generator/src/lovelace-types.ts`:

```ts
/**
 * HA's conditional card: renders `card` only when ALL `conditions`
 * match. Combine with an `or` composite to get an OR-ANY semantic.
 *
 * P1b-5 uses this for the Active Rooms section: per room, an `or`
 * composite of state checks (lights/motion sensors), wrapping a tile
 * that navigates to the room view.
 */
export interface ConditionalCard {
  type: 'conditional'
  conditions: ConditionEntry[]
  card: LovelaceCard
}

/** Single-entity state check: matches when `entity`'s state equals `state`. */
export interface StateCondition {
  condition: 'state'
  entity: string
  state: string
}

/** Composite: matches when ANY child condition matches. */
export interface OrCondition {
  condition: 'or'
  conditions: ConditionEntry[]
}

export type ConditionEntry = StateCondition | OrCondition

/** Tap-action variant: navigate to a sibling view in the dashboard. */
export interface NavigateAction {
  action: 'navigate'
  navigation_path: string
}
```

`TileCard` gains two optional fields:

```ts
export interface TileCard {
  type: 'tile'
  entity: string
  features?: TileFeature[]
  /** Display name override; default is HA's friendly_name. */
  name?: string
  /**
   * Click behavior; default is HA's per-domain default
   * (toggle for lights, activate for scenes).
   */
  tap_action?: NavigateAction
}
```

`LovelaceCard` discriminated union:

```ts
export type LovelaceCard =
  | HeadingCard
  | TileCard
  | ThermostatCard
  | EntitiesCard
  | MarkdownCard
  | GlanceCard
  | MediaControlCard
  | PictureEntityCard
  | ConditionalCard
```

Barrel re-exports in `packages/generator/src/index.ts` add (alphabetical): `ConditionalCard`, `ConditionEntry`, `NavigateAction`, `OrCondition`, `StateCondition`.

**Why `state: string` not `state: 'on' | 'off'`:** scenes/lights/sensors have varied state vocabularies; widening to `string` keeps the type honest and avoids per-domain fan-out.

**Why only `state` and `or` conditions:** Active Rooms only needs single-entity state checks combined with OR. The HA schema supports more (`numeric_state`, `screen`, `user`, `and`); we add what we use, future tickets extend.

## Section building logic

### People — `buildPeopleSection(entities)`

```ts
function buildPeopleSection(entities: NormalizedEntity[]): GridSection | null {
  const people = entities
    .filter((e) => e.domain === 'person' && !e.isHidden && !e.isDisabled)
    .sort((a, b) => a.friendlyName.localeCompare(b.friendlyName, 'en'))
  if (people.length === 0) return null
  const card: GlanceCard = {
    type: 'glance',
    title: 'People',
    entities: people.map((e) => e.entityId),
  }
  return { type: 'grid', cards: [card] }
}
```

`glance` is the right card for People — compact strip with HA-rendered photos. One section, one card, all people in one row.

### Scenes — `buildScenesSection(entities)`

```ts
const SCENE_NAME_FILTER = /test|setup/i

function buildScenesSection(entities: NormalizedEntity[]): GridSection | null {
  const scenes = entities
    .filter((e) => e.domain === 'scene' && !e.isHidden && !e.isDisabled)
    .filter((e) => !SCENE_NAME_FILTER.test(e.entityId) && !SCENE_NAME_FILTER.test(e.friendlyName))
    .sort((a, b) => a.friendlyName.localeCompare(b.friendlyName, 'en'))
    .slice(0, 6)
  if (scenes.length === 0) return null
  const cards: TileCard[] = scenes.map((e) => ({ type: 'tile', entity: e.entityId }))
  return { type: 'grid', cards }
}
```

- Filter is case-insensitive (regex `/i` flag) on both `entityId` and `friendlyName`. `scene.kitchen_test` and `Scene Test Kitchen` are both excluded.
- Cap at 6 scenes after sort, to keep the section visually tidy.
- Each scene gets a plain `TileCard` (no features, no `name` override) — HA tile auto-renders scene name and handles single-tap activation.

### Cameras — `buildCamerasSection(entities)`

```ts
function buildCamerasSection(entities: NormalizedEntity[]): GridSection | null {
  const cameras = entities
    .filter((e) => e.domain === 'camera' && !e.isHidden && !e.isDisabled)
    .sort((a, b) => a.friendlyName.localeCompare(b.friendlyName, 'en'))
  if (cameras.length === 0) return null
  const cards: PictureEntityCard[] = cameras.map((e) => ({
    type: 'picture-entity',
    entity: e.entityId,
    camera_view: 'live',
  }))
  return { type: 'grid', cards }
}
```

`picture-entity` is the type shipped in P1b-2; `camera_view: 'live'` makes HA stream the camera feed in the tile.

### Active Rooms — `buildActiveRoomsSection(groupings, entities)`

For each grouping in `groupings` where `roomId !== 'misc'`:

1. Collect candidate entities from this room's `lights` and `activity` groups.
2. If candidates is empty, skip this room (nothing to drive the conditional).
3. Pick the `primary` entity for tile display: first light if any, else first activity sensor.
4. Build the inner condition: if exactly one candidate, a flat `StateCondition`; otherwise an `OrCondition` wrapping N `StateCondition`s.
5. Build the wrapped tile with `name = roomIdToDisplay(room.roomId)` and `tap_action: { action: 'navigate', navigation_path: room.roomId }`.
6. Wrap the tile in a `ConditionalCard`.
7. After processing all rooms, sort the resulting cards alphabetically by tile `name` (room display name).

```ts
function buildActiveRoomsSection(
  groupings: RoomGrouping[],
  entities: NormalizedEntity[],
): GridSection | null {
  const entityById = new Map(entities.map((e) => [e.entityId, e]))
  const cards: ConditionalCard[] = []

  for (const grouping of groupings) {
    if (grouping.roomId === 'misc') continue

    const lights = grouping.groups.find((g) => g.key === 'lights')?.entities ?? []
    const activity = grouping.groups.find((g) => g.key === 'activity')?.entities ?? []
    const candidates = [...lights, ...activity].filter(
      (e) => !e.isHidden && !e.isDisabled,
    )
    if (candidates.length === 0) continue

    const primary = lights[0] ?? activity[0]!
    const stateConditions: StateCondition[] = candidates.map((e) => ({
      condition: 'state',
      entity: e.entityId,
      state: 'on',
    }))
    const condition: ConditionEntry =
      stateConditions.length === 1
        ? stateConditions[0]!
        : { condition: 'or', conditions: stateConditions }

    const tile: TileCard = {
      type: 'tile',
      entity: primary.entityId,
      name: roomIdToDisplay(grouping.roomId).title,
      tap_action: { action: 'navigate', navigation_path: grouping.roomId },
    }

    cards.push({ type: 'conditional', conditions: [condition], card: tile })
  }

  if (cards.length === 0) return null

  cards.sort((a, b) => {
    const an = (a.card as TileCard).name ?? ''
    const bn = (b.card as TileCard).name ?? ''
    return an.localeCompare(bn, 'en')
  })

  return { type: 'grid', cards }
}
```

**Edge case — single-entity OR:** when a room has only ONE light and no motion sensors, the OR clause has one entry. HA accepts `or` with a single child but it's verbose. Skipping the OR wrapper and emitting a plain `state` condition directly when `candidates.length === 1` is cleaner.

**`roomIdToDisplay` helper:** the analyzer's `RoomGrouping` carries `roomId: CanonicalRoomId`, not a display name. The current pipeline computes display names in `pipeline.ts` (`AnalyzedRoom.displayName`), but that's the SERVER's responsibility. For the generator's home-view, we need a static localized lookup keyed by canonical id. The `room-view.ts` file already has a `ROOM_DISPLAY: Record<CanonicalRoomId, RoomDisplay>` table inline (where `RoomDisplay = { title, path, icon }`).

Extract the existing `RoomDisplay` interface + `ROOM_DISPLAY` table + a `roomIdToDisplay()` getter to a new module `packages/generator/src/rooms.ts`. Both `room-view.ts` and `home-view.ts` import the same source of truth. home-view consumes only `.title` from the result; room-view continues to use all three fields.

```ts
// packages/generator/src/rooms.ts (new file)
import type { CanonicalRoomId } from '@lovelacer/shared'

export interface RoomDisplay {
  title: string
  path: string
  icon: string
}

const ROOM_DISPLAY: Record<CanonicalRoomId, RoomDisplay> = {
  kitchen: { title: 'Kitchen', path: 'kitchen', icon: 'mdi:silverware-fork-knife' },
  living_room: { title: 'Living Room', path: 'living_room', icon: 'mdi:sofa' },
  // ... rest of the existing table from room-view.ts
}

export function roomIdToDisplay(roomId: CanonicalRoomId): RoomDisplay {
  return ROOM_DISPLAY[roomId]
}
```

`room-view.ts` updates to import `RoomDisplay`, `ROOM_DISPLAY`, and `roomIdToDisplay` from the new module instead of declaring them inline. Same data, single owner — no behavior change for room-view tests/snapshots.

## Section ordering + conditional rendering

`buildHomeView()` becomes:

```ts
export interface BuildHomeViewInput {
  entities: NormalizedEntity[]
  groupings: RoomGrouping[]
}

export function buildHomeView(input: BuildHomeViewInput): HomeView {
  const sections: GridSection[] = [buildWelcomeSection(input.entities)]

  const quickStats = buildQuickStatsSection(input.entities)
  if (quickStats !== null) sections.push(quickStats)

  const people = buildPeopleSection(input.entities)
  if (people !== null) sections.push(people)

  const activeRooms = buildActiveRoomsSection(input.groupings, input.entities)
  if (activeRooms !== null) sections.push(activeRooms)

  const scenes = buildScenesSection(input.entities)
  if (scenes !== null) sections.push(scenes)

  const cameras = buildCamerasSection(input.entities)
  if (cameras !== null) sections.push(cameras)

  return {
    type: 'sections',
    title: 'Home',
    path: 'home',
    icon: 'mdi:home-variant',
    sections,
  }
}
```

**Section order** matches `DASHBOARD_GENERATION.md`: Welcome → Quick stats → People → Active Rooms → Scenes → Cameras.

**Empty-state UX:** all four new sections silently disappear when their inputs are empty. No "no people configured" placeholder. Reason: a placeholder is noise for users without those integrations; absence IS the right signal.

**Pipeline change** (`packages/server/src/pipeline.ts`): one-line change at the `buildHomeView` call site:

```ts
// Before
const home = buildHomeView({ entities: state.entities })

// After
const home = buildHomeView({ entities: state.entities, groupings: state.groupings })
```

`state.groupings` is already populated in `runFullPipeline`.

**Hidden / disabled handling:** each builder filters `!e.isHidden && !e.isDisabled` in its first `.filter()`. The Active Rooms candidates likewise filter — even though the analyzer's groupings already filter hidden/disabled at the room view level, the home-view builders are independent consumers of the unfiltered `entities` list, so they re-apply the filter to be safe. The existing `pickQuickStatsEntities` does NOT apply this filter; that's existing behavior we don't touch (out of scope).

**`entityIdsInCard()` helper update** (`packages/generator/src/__tests__/room-view.fixtures.test.ts`): the helper's switch becomes exhaustive over `LovelaceCard['type']` after adding `'conditional'`:

```ts
case 'conditional':
  return entityIdsInCard(card.card)
```

Recurse into `card.card`. Active-rooms tiles aren't emitted by `room-view.ts`, but the helper has to be exhaustive for TypeScript to compile.

## Testing strategy

### Pure-function unit tests — extend `packages/generator/src/__tests__/home-view.test.ts`

Existing `pickQuickStatsEntities` tests stay. Add new describe blocks:

- **`buildPeopleSection`** (4 tests):
  - returns null when no `person.*` entities
  - emits a glance card with all person entityIds when present
  - sorts alphabetically by friendlyName
  - filters out hidden + disabled

- **`buildScenesSection`** (5 tests):
  - returns null when no `scene.*`
  - returns null when all scenes match the test/setup filter
  - emits one tile per surviving scene
  - filter is case-insensitive on entityId AND friendlyName ("Scene Test", "scene.setup_kitchen")
  - caps at 6 scenes (sort alphabetically, take first 6)

- **`buildCamerasSection`** (3 tests):
  - returns null when no cameras
  - emits one picture-entity per camera with `camera_view: 'live'`
  - sorts alphabetically; filters hidden + disabled

- **`buildActiveRoomsSection`** (6 tests):
  - returns null when groupings is empty
  - returns null when no rooms have lights or activity sensors
  - skips rooms with `roomId === 'misc'`
  - room with one light only → emits conditional with single state condition (no OR wrapper)
  - room with multiple lights + motion → emits conditional with OR composite
  - tile points at first light when present; falls back to first activity sensor when no lights
  - tile has correct `name` and `tap_action.navigation_path === room.roomId`

- **`buildHomeView` integration** (3 tests):
  - sections appear in spec order: Welcome, Quick stats, People, Active Rooms, Scenes, Cameras
  - sections that have no qualifying entities are absent (not empty)
  - empty input → only Welcome section appears

Add the `'conditional'` arm. No new test for it (it's tested transitively by the existing room-view fixture snapshots, which don't currently include conditional cards).

The existing test `'returns analyze output plus a config'` mocks the HA client and expects `result.config.views[0]!.path === 'home'` — should still pass since the home view is still emitted at index 0. No new pipeline test needed; the home-view unit tests cover the new builders.
